코드를 이해하고 설계·구현·리뷰하며, 데이터 처리와 실행 플랫폼을 검증 가능한 형태로 개선하는 기술 작업 공간이다.

|---|---|

| [CLAUDE.md](CLAUDE.md) | Claude Code 진입점. AGENTS.md를 가져온다 |

| [guides/platform.md](guides/platform.md) | 데이터 플랫폼, 분석 엔지니어링, K8s·GitOps, 인프라·IaC, 관측·진단 |

## 목적과 범위

하는 일:

- 코드의 실행 흐름·의존성·계약을 이해하고 설계·구현·리뷰한다.
- 데이터 처리와 실행 플랫폼(파이프라인, 분석 모델, K8s, 인프라, 관측)을 검증 가능한 형태로 개선한다.

하지 않는 일:

- 회사 재무·회계 업무, 문의 응대, 티켓 처리, 외부 회신 관리.
- 이전 회사의 코드·업무 문서·분석 결과·데이터·설정·로그·사례·Git 이력·내부 주소를 가져오는 일.
- 이전 작업 공간의 design.md 내용·링크·의존성을 쓰는 일, 원본 문서 저장소를 수정하는 일.

과거 작업은 기술 주제와 관심 방향의 배경으로만 쓴다.

## 기술 배경

지금까지 다뤄 온 작업 주제의 요약이다. 나열한 기술을 모두 운영 환경에 구축했거나 특정 수준으로 숙련했다는 뜻이 아니다.

- Java·Kotlin·Spring·Gradle 백엔드의 코드 분석, 모듈 경계, 의존성, API 계약, 리팩터링과 리뷰.
- SQL·JDBC·데이터 제공 API, 데이터 변환과 스트리밍, 자원 수명과 실패 경로 검토.
- Python·Airflow와 Hadoop 계열의 데이터 처리·메타데이터·조회 경로 검토. Hive·Impala 같은 엔진과 저장·조회 구조에 관심이 있다.
- 컨테이너·K8s·GitOps·CI/CD와 애플리케이션 배포 경로, 배포 관리 API·UI의 상태 정합 검토.
- Grafana 기반 관측, 지표 수집·대시보드, 애플리케이션과 인프라 상태를 연결하는 진단.
- 네트워크·DNS·TLS·권한·스토리지 등 실행 기반과 코드의 연결, AI 작업 규칙과 검증 방식의 개선.

## 현재 집중 분야

데이터 플랫폼, 분석 엔지니어링, K8s 플랫폼, Kotlin·JVM, 코드 구조·코드 리뷰, 인프라·관측.

- SQL·Python·Java는 목적에 맞게 쓴다.
- 플랫폼 UI가 실제로 필요하면 해당 프로젝트의 기존 프런트엔드 스택을 따른다.

## 과거 주제, 관심 후보, 채택 기술의 구분

| 구분 | 뜻 | 기록 위치 |
|---|---|---|
| 과거 작업 주제 | 다뤄 본 범주. 운영 구축 여부나 숙련도를 뜻하지 않는다 | 이 README의 '기술 배경' |
| 관심·검토 후보 | 앞으로 검토할 도구. 예: 분석 엔지니어링의 dbt | 이 README |
| 채택 기술 | 프로젝트에서 쓰기로 결정하고 실제로 설치·설정한 도구와 버전 | 해당 프로젝트 README, 빌드·잠금 파일 |
| 구현 완료 | 실제 검증 명령으로 확인한 상태 | 해당 프로젝트 README·NOTES.md, CI 결과 |

- 현재 이 저장소에는 실제 프로젝트가 없고 채택 기술도 없다.
- 후보 도구를 사용 경험으로 쓰거나 모든 프로젝트의 기본 의존성으로 두지 않는다. 채택은 프로젝트마다 정하고 그 프로젝트에 기록한다.

## 시작 방법

1. Claude Code는 [CLAUDE.md](CLAUDE.md)를, 다른 에이전트는 [AGENTS.md](AGENTS.md)를 읽는다. 두 경로는 같은 규칙을 쓴다.
2. 작업 유형에 맞는 가이드를 AGENTS.md의 '가이드 트리거' 표에 따라 읽는다.
3. 프로젝트 작업이면 그 프로젝트 README의 검증 명령을 쓴다. 프로젝트가 없으면 공통 검증 명령도 없다.
4. 세션을 이어가는 작업이면 해당 프로젝트의 NOTES.md부터 읽는다.

## 프로젝트 추가와 기록

### 구조

- 실제 프로젝트가 생길 때만 `projects/<project-name>/`을 만든다.
- 프로젝트 README에는 목적, 채택 기술과 버전, 실행 환경, 검증 명령을 적는다.
- 소스·테스트·배포 선언·IaC는 소유 관계에 따라 그 프로젝트 안에 두고, 해당 언어·도구의 디렉터리 관용을 따른다.
- 별도 저장소에 있는 코드는 그 저장소에서 직접 작업한다. 여기에 사본을 만들지 않는다.
- 만들지 않는 것: `analysis/`·`review/`·`development/`·`platform/`·`infra/` 같은 작업 유형별 최상위 폴더, 빈 프로젝트, `.gitkeep`, 관심 기술별 샘플.

### 검증 (하네스)

하네스는 AGENTS.md, 필요한 가이드, 프로젝트의 실제 검증 명령, 기존 CI의 조합이다. 별도 실행 장치가 아니다.

- 검증 명령은 프로젝트에서 실제로 채택한 도구로 정한다. Gradle task, 기존 테스트, SQL 계약 시험, Helm·Kustomize 렌더, schema validator, IaC 도구 중 그 프로젝트에 있는 것만 쓴다.
- 같은 명령 묶음을 실제로 반복해서 쓸 때만 기존 빌드 도구·package script·Makefile·Taskfile 중 하나에 작은 진입점을 둔다. CI는 같은 진입점을 호출하고, 프로젝트 README에 사용법을 적는다.
- 만들지 않는 것: 별도 harness 패키지, 검사 registry·profile·독자 ID, 범용 doctor/check/verify/audit CLI, 전용 Git snapshot 엔진, hook 설치기, Stop·Prompt·PostToolUse hook으로 답변을 재생성하는 루프, 매 턴 전수 검사, 규칙 행 수·파일 수·마커 출현을 검사하는 게이트, 빈 test/check target, 성공을 꾸며내는 wrapper.

### 기록

- 세션을 넘겨 이어갈 작업은 프로젝트의 NOTES.md 하나에 남긴다: 목표, 결정, 근거, 미확인, 다음 행동.
- PLAN·CHECKPOINTS·DEBT·사고 원장 같은 관리 문서를 따로 만들지 않는다.
- 오래 유지될 중요한 결정만 프로젝트의 `docs/decisions/`에 남긴다.

### 규칙 개선

- 같은 원인의 실제 작업 실패가 반복될 때만 규칙 개선을 검토한다.
- 해당 규칙이 있었는데 읽히지 않았다면 AGENTS.md의 트리거를 고친다. 검사기·스크립트의 버그면 그 코드를 고친다.
- 모든 실수에 새 규칙을 붙이지 않는다. 규칙은 AGENTS.md와 `guides/`에만 두고 다른 파일에 복제하지 않는다.
