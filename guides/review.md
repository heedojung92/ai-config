# 리뷰 가이드

리뷰와 교차검증·리뷰 결과 반영 직전에 읽는다. 대상 기술의 기준은 [development.md](development.md)의 'Kotlin·JVM'이나 [platform.md](platform.md)의 해당 절을 함께 읽는다. 공통 규칙은 [AGENTS.md](../AGENTS.md)에 있다.

## 비교 범위

리뷰 전에 대상을 정하고 결과에 적는다.

| 범위 | 확인 명령 | 주의 |
|---|---|---|
| 브랜치·PR | `git diff <base>...<head>` | 점 세 개는 merge-base 기준 비교다. base가 최신인지 확인한다 |
| 특정 commit | `git show <commit>`, `git diff <a>..<b>` | 점 두 개는 두 commit의 직접 비교다 |
| staged | `git diff --cached` | 커밋 후보와 같다. unstaged 변경은 포함하지 않는다 |
| worktree | `git diff`, `git status --porcelain` | untracked 파일은 `git diff`에 나오지 않는다 |

- 요청이 모호하면 맥락으로 정하고, 정한 범위를 결과에 밝힌다.
- 영향을 추적하려고 diff 밖의 코드도 읽는다. 다만 범위 안의 변경이 만든 결함과 이전부터 있던 결함을 구분해 보고한다.

## 영향 추적

- 바뀐 심볼의 호출자, 구현·override, 그리고 이름으로 연결된 사용처(리플렉션, DI, 직렬화, 설정 키, SQL 문자열)를 찾는다. 찾은 방법과 범위를 남긴다.
- 계약의 변화를 확인한다: API 응답, 스키마, 설정 기본값, 에러 형식, 시간대·단위, 순서 보장.
- 생성·변경·저장·소비 경로를 따라간다. 한쪽만 바뀌고 반대쪽이 그대로인 곳을 찾는다.
- 배포 순서와 호환성: 롤링 배포 중 구·신 버전 혼재, 마이그레이션과 코드 배포의 순서, 이미 저장된 데이터, 캐시.
- 변경을 검증하는 시험이 실제로 그 경로를 지나는지 본다. 시험이 변경과 함께 수정됐다면 기대값이 무엇에서 왔는지 본다.

## 결함 판정

결함으로 보고하려면 다음이 있어야 한다.

- 발생 조건: 어떤 입력·상태·순서에서 생기는가
- 영향: 누가 무엇을 잘못 받거나 잃는가
- 위치: 파일과 행
- 근거: 코드 경로, 실행 결과, 문서·스펙
- 검증 방향: 결함을 재현하거나 수정을 확인할 방법

다음을 구분해서 보고한다.

- 결함: 위 요소를 갖췄다.
- 질문: 전제(요구, 운영 조건, 의도)를 몰라 판정할 수 없다. 무엇을 알면 판정되는지 적는다.
- 제안·취향: 동작은 맞지만 다른 방식이 낫다고 보는 것. 결함과 섞지 않는다.

판정할 때:

- 부재 주장(호출자 없음, 검증 없음 등)에는 탐색 범위와 방법을 붙인다.
- "현재 경로에서 발생하지 않음"과 "발생할 수 없음"을 구분한다.
- 심각도는 영향과 발생 조건으로 설명한다. 점수를 매기지 않는다.

## 리뷰 결과

1. 결론: 리뷰 범위, 주요 결함 유무, 병합·적용 가능 여부와 그 조건
2. 결함: 위 다섯 요소를 갖춰서
3. 질문
4. 제안
5. 확인하지 못한 것: 읽지 않은 경로, 실행하지 않은 검증

리뷰만 요청받았으면 코드를 수정하지 않는다.

## 수정 피드백 처리

자신의 리뷰 결과나 다른 리뷰어·도구의 지적을 반영할 때 적용한다.

- 지적마다 먼저 독립적으로 확인한다. 리뷰어가 동의하거나 여럿이 같은 말을 해도 정확성의 증명은 아니다.
- 지적마다 다음을 연결해 보고한다: 발견·제안 → 채택 또는 보류와 그 이유 → 수정 위치 → 검증 결과.
- 지적이 틀렸다면 근거(코드 경로, 실행 결과)로 설명하고 수정하지 않는다.
- 수정 diff도 같은 기준으로 영향을 추적한다. 수정이 새 경로를 건드렸는지 본다.
- 시험한 worktree와 커밋 후보가 같은지 확인한다. 다르면 커밋 후보 기준으로 다시 확인한다.
- 같은 지적이 다른 위치에도 해당하는지 확인하되, 공통 원인이 있다는 것과 전체를 고쳐야 한다는 것을 근거 없이 같은 것으로 보지 않는다.
