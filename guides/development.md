# 개발·디버깅·코드 구조

## 시작과 구조 판단

- 목표 동작, 현재 관측, 변경 범위, 유지해야 할 계약을 먼저 정한다.
- 대상 모듈·진입점·호출자·외부 계약·설정·설치 버전을 확인한다. 이름이나 주석만으로 실제 동작을 단정하지 않는다.
- 데이터·상태를 생성하는 곳부터 읽기, 검증, 덮어쓰기, 저장, 후속 소비자까지 추적한다. 기본값·null·실패 경로를 포함한다.
- 모듈은 책임과 변경 이유로 나눈다. 의존성 방향, 순환 참조, public API, 상태 소유권을 확인한다.
- 공통 경로를 쓴다는 이유로 전체 수정이 필수라고 하거나, 현재 미지원이라는 이유로 구현 불가라고 하지 않는다.
- 기존 설정/API, 호출부 변경, 공통 모듈 변경을 비교한다. 가장 작은 diff만 고르지 말고 계약·영향·유지보수 비용으로 선택한다.
- 추상화는 실제 중복·변경 압력을 해결할 때 도입한다. 가상의 확장성 때문에 계층·registry·plugin 체계를 만들지 않는다.

## 구현과 진단

- 기존 언어·프레임워크 관용과 호환성을 유지한다. 요청하지 않은 의존성 교체나 무관한 정리를 섞지 않는다.
- 주석에는 이유·계약·함정·선택의 귀결을 적는다. 코드를 그대로 읽어 주는 설명이나 작업 일지를 넣지 않는다.
- 원인은 관측과 메커니즘으로 설명하고, 같은 증상을 만드는 다른 가설을 가르는 확인을 한다. 설명 가능한 코드를 찾은 것만으로 실제 원인이라 하지 않는다.
- 실패를 재시도할 때는 무엇을 새로 알았고 어떤 가설·입력·조건을 바꾸는지 분명히 한다. 같은 실패를 반복하는 자동 루프를 만들지 않는다.
- 성능·자원·동시성·상태 전이가 영향을 받으면 해당 경로를 확인한다. 근거 없는 위험 점수나 임의의 성능 수치를 만들지 않는다.

## 검증

| 변경 | 판정 기준 |
|---|---|
| 결함 수정 | 가능한 경우 동일 입력의 수정 전 실패·후 통과 |
| 새 기능 | 요구·계약에서 정한 독립 수락 조건 |
| 리팩터링 | 유지해야 할 입력·출력·상태·부작용 |
| 의존성·설정 변경 | 설치 버전, 호환성, 실제 소비자·실행 경로 |
| 계측 코드 | 본래 기능의 응답·상태·헤더·부작용·지연·자원 영향 |

- 기대값을 구현에서 그대로 복사하지 않는다. 요구·계약·확인된 입력에서 얻는다.
- 기존 테스트·빌드·린트·정적 분석을 먼저 사용한다. 필요한 경우에만 작은 재현 코드나 회귀시험을 추가한다.
- 시험의 실제 실행과 필요한 경로를 확인한다. 0건, 필요한 skip, 다른 경로의 통과를 해당 경로의 근거로 세지 않는다.
- 같은 계약의 검증 결과를 재사용할 때는 변경본·입력·환경·소비자 연결이 여전히 대응하는지 확인한다.
- 요구된 확인이 통과하면 끝낸다. 추가 시험은 남은 구체적 위험과 그 결과로 달라질 판단이 있을 때 선택한다.
- 직접 확인하지 못한 경계와 결론에 미치는 영향을 밝힌다. 컴파일이나 mock 통과를 실제 서비스·플랫폼 성공으로 확대하지 않는다.

## 보고

무엇이 바뀌었는지, 왜 필요한지, 무엇을 실제로 실행해 확인했는지, 남은 미확인을 설명한다. 고쳤다는 판단은 목표 소비자 관측이나 독립 수락 조건에 연결한다. 계획·추정·실행 결과를 한 문장에 섞지 않는다.
